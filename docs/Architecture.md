# Xythos v1 — Architecture and Milestones

This plan covers version 1 as scoped in [Requirements.md](Requirements.md): local NAM blocks, local IR blocks, a delay block, a reverb block and a compressor block, plus everything around them (chain, split/merge, tuner, metronome, presets, settings). Later features (IR loader, other effect categories) are not built in v1, but the design leaves room for them.

## 3. Signal flow

```
in ─► Input level ─┬─► Chain (up to 32 blocks, optional split A/B → merge) ─► Bass/Mid/Treble ─► Output level ─► (+ metronome) ─► Limiter ─► meters ─► out
                   │
                   └─► boost ─► Tuner analysis (dry input)
```

- **Global bypass** passes the input straight to the output (meters keep running).
- **Tuner mute** silences the guitar path only; the metronome stays audible.
- **Metronome** is mixed in before the limiter, so clicks cannot clip the output.
- **Mono mode** takes the first input and processes one channel, output to both sides. It turns stereo where a mono sound needs to spread (owner, 2026-10-29: a mono guitar with two amps panned apart): after a split's merge, and at a block whose descriptor has `stereo` set (the Delay, for its Stereo and Ping-Pong modes); from there on blocks run on two channels. This is decided by the chain's layout alone (a bypassed stereo block still counts), so blocks never switch channel counts while playing. **Stereo mode** runs every block on two channels; a NAM block then holds two model instances (double CPU, as agreed).

## 4. Engine design

### 4.1 Blocks are modular

Every effect is a subclass of `Block`:

```cpp
struct BlockDescriptor {
    const char* typeId;         // "nam", "delay", "reverb" — stored in presets
    const char* displayName;
    Category category;          // NAM, IR, Delay, Reverb, ... (Add Block dialog)
    ParamSpec params[kParamsPerSlot];
    Block* (*create)();
};

class Block {
public:
    virtual void prepare(double sampleRate, uint32_t maxFrames, int channels) = 0;
    virtual void process(float** io, uint32_t frames) = 0;   // real-time safe
    virtual void setParam(int index, float value) = 0;
    virtual uint32_t latency() const { return 0; }
    virtual void reset() = 0;
    virtual void setTempo(double bpm) {}            // host tempo, before every process()
    virtual float meter() const { return 0; }       // a level the UI shows, e.g. gain reduction
};
```

A block's `meter()` reaches the UI through one output parameter per slot (`kParamSlotMeterBase + slot`).

New effects are added by writing one class and one registry line. Removing an effect is deleting both. The Add Block dialog, parameter names and preset loader all read from the registry.

### 4.2 Real-time safety

The audio thread never allocates, locks, or touches files.

1. Edits (add/move/remove block, change model, split/merge) update the `ChainState` in the UI, which sends it to the DSP as the `chain` plugin state.
2. The DSP's `setState()` (always called off the audio thread) builds a new graph. NAM files are loaded and warmed up there, and blocks that didn't change are reused, so their state (delay tails, reverb tails) carries over.
3. The finished graph is handed to the audio thread through a lock-free single-slot exchange. The audio thread picks it up at the start of a buffer, fades the chain output out over 5 ms, swaps, and fades back in over 5 ms. (A fade out/in rather than a crossfade, because reused blocks can't run in two graphs at once.)
4. The old graph goes back through a lock-free queue and is deleted off the audio thread.

**Host activation.** DPF counts the plugin as active before `activate()` returns, and its VST3 `process()` activates the plugin itself, so a host can run audio while `activate()` re-prepares the engine (hosts call it from different threads; Reaper when an FX is switched off and on). The plugin keeps them apart with two flags (sequentially consistent): `activate()` waits for a `run()` in progress, and `run()` outputs silence while `activate()` prepares. Activation prepares and resets every block, so a block must play on after `prepare()` + `reset()` just as a fresh one does (`tests/BlockSanityTests.cpp` checks every block type). The IR block didn't: FFTConvolver's `reset()` unloads the IR, which silenced any chain with a cab after Reaper switched the FX off and on (2026-10-29); the block's `reset()` now leaves its convolvers alone.

**NaN recovery.** A NaN or infinity stays in every recursive filter for good, which would leave the plugin silent until it's removed. The engine replaces non-finite input samples with silence, silences a non-finite chain output before the tone stack and limiter (resetting those if they ever see one), and reports it (`takeChainFault()`); the plugin's exchange thread then rebuilds the chain with fresh blocks (`forgetBlocks()`, at most once a second).

Parameter changes (knobs, automation, MIDI) don't rebuild anything. They go straight to the block through its slot, with per-parameter smoothing.

Parameter values live in the host. `ChainState` also stores each block's normalized values and bypass, but only for presets and undo: when one is loaded, the UI pushes those values to the host. The DSP always reads the host's values.

### 4.3 Parameter slots (DAW automation and MIDI)

The host sees a fixed parameter list:

- **Global**: input mode, input, bass, middle, treble, output, global bypass, limiter on/off, tuner on/off, tuner mute, metronome on/off, metronome volume, and a few more.
- **32 slots × 17 parameters**: slot bypass plus 16 block parameters (8 until the Doppelganger Delay needed more; changed before release, so no saved automation was affected). That's ~550 slot parameters, which hosts handle fine.

Each block is assigned a free slot when it is created and keeps it for its whole life, so dragging a block to a new position doesn't break automation. Host-facing names are generic ("Slot 05 · P2"). The UI shows real names, and the slot number in the block panel ("Distortion · Slot 05") so users can find it in their DAW; the tile shows the block's category (it showed "S05" until 2026-10-25, owner's request).

**MIDI learn**: right-click any control (or a block tile, for its bypass) → "MIDI Learn", then move a controller. The mapping (CC + channel → host parameter) is stored in the chain state, so it is saved with the project, in presets and in undo, and reaches the DSP by the same routes as the chain. Incoming CCs are applied at the start of each buffer in `run()`. The DSP reports each CC through hidden output parameters: the UI learns from them, and writes mapped values to the host, since LV2 hosts mostly can't take parameter changes from the DSP (in VST3 the DSP also reports them itself). Right-click → "Clear MIDI" removes a mapping; removing a block removes its mappings.

**Program Change** (owner, 2026-11-02; footswitches like the M-Vave Chocolate send only these out of the box): MIDI learn takes one too (a `MidiMapping` with `program`, `"pc": true` in JSON). It can't set a value, so what it does depends on the control (`ChainState::programAction()`, `globalProgramAction()`): a block's bypass, a block's Toggle controls and the global switches flip on each press (`flippedValue()`); Momentary controls and the looper's Rec/Dub, Play/Stop, Clear and Tap are pressed: 1 for one `process()` call, then 0 again (`Engine::midiProgram()`); knobs and choices take none, and learning one onto them says so. The DSP reports Program Changes in hidden outputs (MIDI Last Program, MIDI Program Value, MIDI Program Count, the count last since hosts tend to report changes in index order) for learning and for the UI to pass flips on to the host, as with CCs.

A Program Change no mapping takes may load a preset: `Settings::programPresets` (program -> preset path; any channel), set in Manage Presets (a Program button per preset: click, press the footswitch; a second click removes it). The plugin's exchange thread loads the preset itself (`loadProgramPreset()` in the plugin: `loadPresetFile()` with the library indexes' last scans for missing files by hash, `retireLoopers()`/`migrateBlocks()` from `src/state/ChainMigration.*` as the UI does, the globals and block values into the engine, then the chain), so it works with the window closed. `run()` tells the host the new values (`requestParameterValueChange()`, at most 64 a buffer). The DSP then bumps Preset Program (count * 128 + program); an open UI takes the chain from the exchange file as one undo step and sets the host's values too. Limit: LV2 hosts without the port change request extension (Reaper) don't learn the values while the window is closed, so a project saved then keeps the chain with the old values; VST3 has no such limit.

### 4.4 Split, merge and the second core

- The chain has at most one split. `ChainState` keeps the blocks in one list, left to right, plus `split = {begin, end}`: blocks `[begin, end)` run in the two branches, and each of them has a `branch` tag (A or B). Blocks before `begin` run before the split, blocks from `end` on after the merge. A branch may be empty; it then carries the signal unchanged (a parallel dry path). `ChainState` has helpers (`sectionIndices`, `insert`, `remove`, `move`, `addSplit`, `removeSplit`) that keep the range and tags consistent. Removing the split keeps every block: the branches become serial, A then B. The chain JSON went to version 2 for this; version 1 still loads.
- The merge has A/B balance, and a level, pan and phase invert per branch. These are host parameters (`kParamMergeBalance` … `kParamMergeInvertB`), so they can be automated; one set is enough, as there's only one split. Presets save them. Balance keeps both branches at full level in the middle and turns the other one down towards either end. Pan works like a balance control, in Mono mode too (the chain is stereo after the merge; a branch still mono plays on both sides). **Align** (`kParamMergeAlign`, ±5 ms; owner, 2026-10-29: two similar amps summed sounded bad, likely a few samples apart) delays branch B (right) or A (left) by a fractional, smoothed amount (Hermite reads), to line up two amp captures; it adds no reported latency. At 0 it passes the branches through exactly. All merge gains are smoothed, so phase invert fades through zero instead of clicking. Invert A and B are off by default (owner, 2026-10-29: Invert A was on for a while, but out-of-phase captures aren't common); a new split resets the merge controls to their defaults.
- If the two branches have different latencies, the shorter branch is delayed to match (`DelayLine`), and the host is told the longer one.
- **Parallel processing** (on by default; Settings > Parallel processing. The DSP reads the setting when it builds a chain, and the UI resends the chain when it changes): a `ParallelWorker` thread is woken each buffer to run branch B while the audio thread runs branch A, and the audio thread then waits for it. Waking is lock-free (an atomic counter with `wait`/`notify_one`), and the audio thread spins briefly, then yields, until the worker is done. The worker copies the audio thread's scheduling policy and priority on its first job (Linux), or uses `THREAD_PRIORITY_TIME_CRITICAL` (Windows), and flushes denormals like a host audio thread. If the worker is late, the audio thread keeps waiting (no extra latency, but a risk of a dropout on an overloaded machine). With the toggle off, or with an empty branch B, both branches run in sequence on the audio thread. The worker thread is only started once a chain needs it.
- UI: with a split, the chain view has two rows of slightly smaller tiles: branch A and everything outside the split on the top row, branch B below, and a tall merge tile where they join (click it for the merge controls, × to remove the split). Each branch and the part after the merge has its own "+".  While there's no split, hovering the gap before a block (or before the "+") shows a small split icon on the signal line; clicking it adds an empty split there (both branches start empty). Blocks are dragged between rows and sections freely; a line in the highlight colour shows where a block will land.

### 4.5 Latency

- All v1 blocks are zero latency by default. The engine adds up block latencies along the path, aligns branches, and reports the total to the host (DPF `setLatency`). The pitch-following blocks can add latency with their Lookahead (4.11, "Note tracking"), and the pitch blocks with their HQ mode (4.11, "HQ pitch shifting"; about 150 ms, off by default). A bypassed block with latency still delays its signal (`Node::bypassDelay`), so bypassing it doesn't change the timing or the reported latency.
- **Sample rate**: NAM models record the rate they were trained at, usually 48 kHz. If the host runs at that rate, there's no resampling. Otherwise the NAM block resamples with a low-latency resampler (a few samples), reports that latency, and shows a small warning badge on the block.

### 4.6 The NAM block

- Loads A1 and A2 files through NeuralAmpModelerCore (pinned to v0.6.0, which includes the A2 fast path). Full/Lite is selected with `nam::SlimmableModel::SetSlimmableSize` (1.0 = Full, 0.0 = Lite); it isn't real-time safe, so it's applied off the audio thread.
- A2 size: global default from Settings, with a per-block override.
- Normalization (per-block toggle): uses the loudness value stored in the `.nam` metadata to bring models to a common level. Models with no loudness value are left as they are, with a badge saying so.
- Block parameters: input gain, output gain, normalization on/off, A2 size (Full/Lite).

### 4.7 Delay block

Parameters: time (ms, or a note value when synced), tempo sync on/off, feedback, mix, tone (low-pass in the feedback path), mode (mono / stereo / ping-pong), stereo spread, modulation depth. In stereo mode, left and right have separate lines, offset by the spread setting.

- Time changes glide (a smoothed, fractionally read delay time), like a tape or analog delay, instead of clicking.
- Synced, the Time knob picks from 14 note values (1/1 down to 1/32, with dotted and triplet values); the host tempo comes from DPF's `TimePosition`, 120 BPM when the host doesn't report one. Max delay is 4 s.
- The feedback path has a fixed 40 Hz high-pass, the Tone low-pass and a soft limit above half scale, so 100% feedback stays bounded.
- Ping-pong: the input (summed to mono) enters on the left, repeats alternate left and right.
- Mix: the dry signal stays at full level up to 50%, and the wet signal reaches full level at 50% (also used by the reverb).

### 4.7b Doppelganger Delay block

The owner's idea: a delay whose echoes alternate between two effects. With the default order, echoes 1, 3, 5… are flanged and echoes 2, 4, 6… are chorused, and each echo has only its own effect (they don't stack).

- An ordinary feedback delay keeps every echo in one loop, so effects in the loop would pile up. Instead, one clean line repeats at 2T with feedback g²: `s(t) = x(t) + g² F² s(t−2T)`. Reading it at T gives the odd echoes, `g F s(t−T)`; the loop's own feedback term gives the even ones. These are exactly the echoes of a delay with time T and feedback g, split by parity, so each stream goes through its own effect outside the loop. F is the Tone low-pass (and a 40 Hz high-pass), once per repeat, so repeats darken like the Delay block's.
- Flanger: a 0.25–5.25 ms swept delay with regeneration (−95…95%), level-compensated. Chorus: 1–3 voices around 10 ms, spread evenly around the LFO cycle. Each has rate, depth and mix (0% = clean echoes).
- Order swaps which effect gets the odd echoes. Width offsets the right channel's LFOs (up to 180° for the flanger, 90° for the chorus). Bounce leans flanged echoes left and chorused echoes right (stereo mode).
- Time, Sync, Feedback and Mix work as in the Delay block (same note values; synced up to 4 s, so the line holds 8 s).
- 16 parameters: time, sync, feedback, mix, tone, order, width, bounce, then flange rate/depth/regen/mix and chorus rate/depth/voices/mix.

### 4.8 Reverb block

An algorithmic reverb written in-house (Dattorro-style plate/hall network). Parameters: type (room / hall / plate), decay, pre-delay, damping, low cut, high cut, width, mix. Mono input gives a stereo-wide tail when the plugin is in stereo mode.

- One figure-eight tank (Dattorro 1997) voiced three ways: Plate is the original sizes; Hall scales the tank by 1.45 with deeper, slower modulation; Room scales it to 0.42 with less diffusion and adds early reflections tapped from the pre-delay line.
- Decay is the RT60 in seconds; the tank's decay gain is computed from it and the tank's loop time, so the set time holds for every type and sample rate (tested).
- Buffers are sized for the largest voicing in `prepare()`, so changing type on the audio thread only changes read positions.

### 4.8b Compressor block

Added to v1 at the owner's request. Studio style, feed-forward: stereo-linked peak detector, soft-knee gain computer, attack/release smoothing of the gain in dB, then makeup gain and a dry/wet mix for parallel compression. Parameters: threshold, ratio, attack, release, knee, makeup, mix. Its gain reduction is shown in the block panel through the block meter.

### 4.9 Tuner

- The input (after the Input level, before the chain) is copied into a lock-free ring buffer, and the analysis runs on a DSP-side thread every 20 ms while the tuner is on, never on the audio thread (`engine/tuner/Tuner`). Stereo input is analysed as the sum of both channels.
- The detector doesn't depend on the level, so quiet inputs work as well as loud ones (this is what the "boost" in the signal flow stands for): only a gate at -74 dBFS RMS decides whether there's anything to analyse.
- Pitch detection (`engine/tuner/PitchDetector`): McLeod Pitch Method (as in Fretbored) on an ~85 ms window (4096 samples at 48 kHz, enough for 31 Hz), FFT autocorrelation and parabolic peak interpolation, which on its own is good to about ±0.4 cent. It is then refined: a Hann-weighted normalized cross-correlation over a whole number of periods, low-passed above the 6th harmonic, measured at the largest multiple of the period that fits and divided back. The refinement uses up to four windows of audio (~340 ms) when the note has been steady that long, which makes it far less sensitive to noise.
- Only audio at a steady level is analysed: levels are compared in chunks of whole periods, and a window that isn't steady (a note starting, stopping or changing) gives no reading at all, rather than a wrong one. The UI keeps showing the last note for a second.
- The detected frequency and clarity are output parameters, so this works when an LV2 host runs the UI in a separate process. The UI takes the median of the last five readings (starting over when the note clearly changes) and works out the note and cents from the reference pitch. Arc (the needle, the default; owner, 2026-11-02, needle concept 4 of a third round of mockups, turned to point up: a bolt of lightning from a pivot at the bottom to a ±50 cent scale arc, its noise smooth over time (`fArcPhase`, faster further off) so it writhes at the frame rate, with forks fading in and out; it calms as the pitch comes in and is a straight green beam in tune; `drawArc()`), Runes (the default from 2026-10-31 to 2026-11-01, the owner's pick from ten mockups: 21 crystal glyphs of 5 cents each over ±50, lit from the centre out to the pitch, only the centre one, green, in tune; `drawRunes()`) and Aurora (the strobe; owner, 2026-11-02, strobe concept 6 of the third round: three curtains of light over a horizon, the fundamental and two octaves, drifting right when sharp and left when flat, still and green in tune; rays drawn additively in the highlight's colour where they stand; `drawAurora()`) views (Arc and Aurora replaced the Vernier, two rings of ±50 and ±10 cents, and Chevrons, rows of chevrons marching the way to tune, the owner's picks of 2026-10-31 from a second round of mockups; before those, a knob-style arc and three rows of bands; Hive, strobe 6, a honeycomb with bands of light sweeping across it, was removed on 2026-11-01: it looked incredible but was too strange to use) are drawn in the UI; the view is hidden parameters, so it's saved with the project: Tuner Runes (`kParamTunerRunes`, added after the slots' latches, so the old indices stay; default off since 2026-11-01) over Tuner Strobe (Arc or Aurora). Tuner Chevrons (`kParamTunerChevrons`, after Tuner Runes) picked Chevrons over Hive and is unused now (host parameters are never removed). Picking a view sets the other parameter to match.
- While the tuner is on, the guitar is muted by default (Tuner Mute; also in global bypass); the metronome stays audible.
- Reference pitch A4 is adjustable from 415 to 466 Hz.
- **Accuracy target: ±0.1 cent from 31 Hz up to the 24th fret of the high E string (~1319 Hz)**, checked by tests at 44.1, 48 and 96 kHz on every half semitone, with pure tones, harmonic-rich tones and noisy tones with a weak fundamental (worst case about 0.01 cent), and through the start and end of notes (a gated tone; a plucked-string-like note whose harmonics decay at different rates). No recorded signals yet: the tests are synthetic.

### 4.10 Metronome

- Runs in the DSP (`engine/metronome/Metronome`), scheduled to the exact sample: each beat's time is kept as a fractional sample position and rounded, so the tempo never drifts, whatever the buffer size. Clicks are mixed in after the Output level and before the limiter, so they can't clip the output; the tuner's mute doesn't silence them. Global bypass does (it's a true bypass).
- **Free mode** (default): its own tempo, starting on beat 1 when switched on. Switching off lets the click that's sounding play out (cutting it would pop).
- **DAW sync** (switch): follows the host's tempo, time signature and transport position (DPF `TimePosition`): clicks fall where the host's beat position crosses a beat or subdivision, only while the transport plays. Each click has an ID (beat × 16 + subdivision), so a click on a buffer boundary is never played twice or missed, and a jump (loop, locate) starts over at the new position. The tempo trainer doesn't apply in sync mode (the host sets the tempo); the gap trainer does, on the host's bars.
- Features match Fretbored: 20–300 BPM (slider, ±1/±5, keyboard), tap tempo, 1–16 beats over 2/4/8/16 with beat grouping (cycled through every split into 2s and 3s; the default follows Fretbored, e.g. 7/8 = 2+2+3), per-beat accents (accent/normal/soft/mute, set by the grouping and by clicking a beat), the eleven subdivisions, Classic/Digital/Beep sounds with separate volume for subdivisions, step and gradual tempo trainer (also slowing down), gap trainer, and a visual pulse (the pendulum sweep was removed at the owner's request, 2026-10-23: at host redraw rates it looked choppy). Fretbored's "visual sync" offset (for Bluetooth speakers) isn't needed in a plugin.
- **Every setting is a host parameter** (tempo, volume, on/off and sync are automatable; the rest are hidden), so it works the same in every host — including Reaper's LV2, which doesn't deliver UI state messages — and is saved with the project. The accents are 16 parameters; the grouping is a bit mask of the beats that start a group, kept only for the UI. The DSP reports the beat being heard, a beat counter (the UI pulses when it changes), the bar, the tempo being played and the gap trainer's mute as output parameters.
- **Panel**: the top bar's Metronome button switches it on and off (and flashes on every beat); ▾ next to it opens the panel, which covers the chain while it's open. Shortcuts while the panel is open (so only while the plugin window has the keyboard focus): Space start/stop, ↑/↓ tempo (Shift: 5 BPM), T tap.
- Sounds: all generated in code at the host rate, no samples (owner's decision, 2026-10-23, so every sound is our own). Classic recreates Fretbored's click, which turned out to be a formula: fitting the owner's two WAVs gave exactly e^(-t/50 ms) (0.5 sin wt + 0.15 sin 2wt + 0.05 sin 3wt), 50 ms long, at 1500 Hz (accent) and 1000 Hz (beat and subdivisions), with zero residual; with the same 0.5 ms / 6 ms edge fades the generated clicks matched the old samples to -56 dB (16-bit rounding). The owner then raised it two semitones (2026-10-26): 1683.6 and 1122.5 Hz. Digital (a short band-limited square wave) and Beep were already generated in code.
- The top bar also has the Fretbored link (opens the web app in the default browser: `xdg-open` / `ShellExecute`).

A note starting next to (within 2 semitones of) a fading voice takes over that voice's phase, level and pitch, so bends and slides move one voice from band to band. - **Robot Filter**: an SVF whose cutoff jumps to a new held value on each clock tick (random, a fixed 8-step random loop, or the input level), with a glide on the octave position. **Talk Box**: three SVF band-passes on the first three formants, interpolated (on a log scale) along a vowel path.

**Modulation Sweeper** (the owner's idea, 2026-10-23): two or three of chorus, flanger, phaser and vibrato, picked by the user (Effect 3 can be None), that the block moves between. Each Sweep Rate step it moves on to the next effect in the pattern (Back & Forth: 1 2 3 2 1..., Cycle: 1 2 3 1...); Glide is the share of each step spent crossfading (raised-cosine, gains adding to 1 because the effects all carry the dry signal; never shorter than 15 ms, so 0% doesn't click). Shared DSP (`src/engine/dsp/`):

- **Oversampler**: the drives clip at 4x through polyphase IIR half-band filters (HIIR-style allpass pairs designed in code): flat to 0.49 fs, aliases more than 70 dB down, no added latency (IIR group delay only). Clipping curves are in `Waveshapers.hpp` (x / (1 + |x|^n)^(1/n), square roots only).
- **Svf**: TPT state variable filter, stable when the cutoff moves every sample (wahs, auto wah, filter, synth). `OnePole` and `EnvelopeFollower` live with it.
- **Lfo** (phase accumulator, any phase offset for stereo) and **RandomLfo** (smoothed random, for drift). `TempoSync.hpp` maps a synced knob to a note value: a time knob has the longest note at the top (1/1 down to 1/32); a rate knob has its own list from 4 bars and 2 bars down to 1/32, the fastest at the top. The descriptor's `syncParam`/`syncedParam`/`syncedIsRate` tell the UI.
- **PitchShifter**: delay-line voices, two Hann-crossfaded taps whose delays move at (1 - ratio) samples per sample and jump by the window at the end of a sweep. Polyphonic, no reported latency; the shifted sound trails by about half the window (the Window control). The splices are made phase-coherent: a **PeriodFinder** (autocorrelation on a 12 kHz copy, every 8 ms, lags 7-60 ms, parabolic peak) finds the signal's repetition period, which for chords is their approximate common period (two root periods for a power chord, four for a major triad); the tracked note is the fallback. The window becomes a whole, even number of that period, each tap takes the new window when it jumps, and each jump is steered (a few percent of the window per jump, so it never clicks) to land exactly half a window from the other tap. Shifted notes and chords then keep 95-100% of their energy at the shifted partials (tested; it was 0-20% with a plain window, which is the warble cheap pitch shifters have). Costs about 2-3% of a core per pitch block in stereo. Used by Pitch Shifter, Whammy, Poly Octave, Harmonizer and Shimmer (Shimmer keeps a plain window: its reverb tail has no period).

HQ shifts with `dsp/SpectralShifter.hpp`, a wrapper around Signalsmith Stretch (MIT; STFT phase vocoder with peak-locked phases), vendored in `deps/signalsmith-stretch` with our pitch-accuracy fixes (its README: peak frequencies from the phase advance, phase advance interpolated before de-rotating, the bin's own temporal prediction in the vertical step; upstream a shifted steady tone was up to 13 cents off a fifth or octave up and 44 cents an octave down, now 0.3 and 5) and Signalsmith Linear (submodule) for its FFTs. Block 120 ms, interval 30 ms, split computation (the work spread evenly over each interval): latency about 150 ms (input 60 ms + output 90 ms), about 1% of a core per voice and channel. 80 ms (100 ms latency) was tried: an open E chord an octave down kept only 76% of its energy at the shifted partials (120 ms: all of it; the delay-line shifter: 90%), and 40-60 ms smeared the low strings. On single notes HQ is much cleaner than the delay-line shifter at any setting (no splice warble); two octaves down neither is good. In the PitchBase blocks each voice is a shifter, the dry signal goes through a matching delay, and the block reports the latency; blocks process in 32-sample chunks (`beginChunk()`, `dryIn()`, `voice()`), a voice's ratio taking effect from the next chunk, and voices whose level is at zero are skipped (reset when turned up). The Window and the period finder aren't used. The Harmonizer's tracked shifts are delayed by the shifter's input latency (in whole chunks) so a new harmony starts with the note it belongs to; its latency is the lookahead's plus HQ's. Shimmer and Pitch Delay report no latency: Shimmer shifts the tail chunk by chunk inside its feedback loop (the shifter's delay only delays the regeneration), and Pitch Delay reads each repeat that much earlier from its delay line so echoes land on time (repeats shorter than the latency play at the latency). The Organ and Arpeggiator have no HQ mode (their swell and steps follow the input as it arrives). Tests: `tests/HqPitchTests.cpp`.
- **PitchTracker** (reworked on 2026-11-09: 25 Hz up, no fixed threshold, the common-period test; "Tracking rework" above): YIN (cumulative-mean normalized difference, absolute threshold) on a copy decimated to 12 kHz, every 4 ms, 28-1500 Hz (60 Hz until 2026-10-29, which missed a 7-string's drop A; now down to a 5-string bass's low B, 31 Hz, at the owner's request), then refined at the full rate around the estimate. The difference at each lag is over a window of one lag (at least 2 ms; it was a fixed 17 ms), so an estimate needs about two periods of the note, and it is divided by the two windows' energy, so a fast swell or decay (a pick attack, a palm mute) doesn't read as unclear. On plucked strings (Karplus-Strong, whose fundamental is often weaker than its harmonics) it holds the note to 0.1 cent (tested). It replaced a zero-crossing tracker that locked onto harmonics of low plucked notes. A pitch under 60 Hz needs its fundamental within 9 dB of its 2nd to 4th harmonics: strings left ringing together repeat at their notes' lowest common period, often down there, with nothing at it. The difference function runs over a copy of the newest samples with running sums of squares (cheaper than before at twice the range: about 1% of a core for the NoteTracker). In the NoteTracker, a new note at the mains' 50 or 60 Hz (within 0.2 semitones) needs a pick, so hum after an amp doesn't start notes in the silence. Used through the NoteTracker by the synths, the Harmonizer and the Octave, and directly, as a fallback to the PeriodFinder, by the pitch-synchronous windows.
- **NoteTracker** (2026-10-23; the owner found the synths, pitch pedals and octaver playing notes not played and missing notes; repeated notes and mutes added on 2026-11-09, "Tracking rework" above): turns the PitchTracker's estimates into notes. Its own level follower holds for a period and then falls fast (the tracker's released over 80 ms, so notes ran on past every mute); the gate opens 12 dB over a followed noise floor (rising only between notes) and closes 50 dB under the note's peak; a level 20 dB under a 20 ms follower is a mute, and the muted tail can't start a note again. A note starts when two estimates in a row agree, with an aperiodicity under 0.3; once it plays, estimates within 0.6 semitone follow it however unclear (bends, vibrato, the decay). Two clear estimates of another pitch end it (a new note without a detected pick); 35 ms without a clear pitch ends it too. A pick (OnsetDetector on the level, or on the level high-passed at 2 kHz, where the pick's click stands out while an old note rings) ends the note before it; it may start a new note only once confirmed by the average level (3 ms) rising 1.25x or holding over 0.3 of its level for 12 ms: a mute clicks too (a finger landing, or the synthetic string's step), and then the level falls, so the click counts as a mute and the tail can't start a note (the average, because the peak follower holds a click's spike). With it the benchmark's phantom notes went from 5 to 0. The Pick Filter: a new note must also hold that long. **Lookahead**: the output runs that far behind the input, and a new note is written back to its pick (or to 8 ms before its first estimate), so notes start on time at the pitch found after the pick.
- **Fdn**: 8-line Householder feedback delay network with input diffusers, per-line damping and RT60 gains, two modulated lines; it can freeze (lossless loop, input shut). Used by Shimmer, Freeze, Bloom Reverb and Gated Reverb.
- **OnsetDetector**: a new pick attack (a fast envelope jumping to twice a slower one, over -50 dB, at most every 60 ms). Used by the Organ, the Sustainer, Bloom Reverb and the NoteTracker.

Notes:

- **Levels**: default settings stay within a few dB of bypass (drives a few dB louder, like a pedal set at unity-plus).
- **Beat-locked LFOs**: while the host's transport plays, the engine passes each block the song position (quarter notes, at the start of each chunk) through `Block::setSongPosition()`. Synced tremolo, flanger, phaser and filter lock their LFO phase to it (cycles counted from the song's start; the tremolo's loudest point lands on the beat), only correcting when off by more than 0.1% of a cycle. Stopped, they run free at the synced rate.
- **Noise gate key**: `Block::setRigInput()` gives every block the chain input (after the input level). With Key = Rig In, a gate after an amp opens and closes on the clean guitar.
- **Momentary parameters** (`ParamScale::Momentary`, the looper's Rec/Dub, Play/Stop, Clear): 1 while held; blocks act on the 0 → 1 edge, so a MIDI footswitch's press/release maps directly. The UI holds a quick click for 80 ms so the press can't fall inside one audio buffer with its release. With a Latch control (Kill Switch, Beat Repeat, Tape Stop) a press toggles a latched state inside the block. No host parameter holds it, so it's saved separately: blocks report it (`Block::latched()`, bit i = parameter i), the engine publishes it per slot as a hidden output (`slotLatchParam()`), and the chain JSON carries it as each block's `latched`, filled in from the live state when the UI saves a preset (or sends the chain) and when the DSP's `getState()` saves the project. New blocks start with the chain's `latched`; blocks the engine keeps take it only from a preset being loaded (`restoreLatches`, never saved), so an ordinary resend can't undo a press. A block keeps restored bits until its Latch goes from on to off, since the host may restore Latch after the chain. The looper's state (the loop itself) isn't saved.
- **Looper, global** (owner, 2026-11-01): the looper left the chain. Its DSP is `Looper` (`src/engine/looper/Looper.hpp`, header-only, extracted unchanged from the block); the engine owns one, run after the output level and before the metronome and limiter (`Engine::processLooper()`), so it records what's heard, plays on whatever the chain becomes (presets change the chain, not it), and its count-in clicks join the metronome's. A loop makes the output stereo, so a stereo loop stays stereo under a mono chain. Its 16 controls are host parameters after the tuner's (`kParamLooperBase`, `looperParam()`, LooperParam order, real values; the footswitches and the sound automatable, the set-up hidden; all MIDI-mappable, so footswitches can map to them), applied when they change (Tap sets the BPM inside it, which the host's unchanged value mustn't undo). Re-preparing at the same rate keeps the loop. Outputs: `kParamLooperState` (`LooperReport::encodeState()`: state, the pass being recorded, lanes, generation), position, the count-in click, the length, and 8 waveform cells. **The waveform**: the looper keeps each pass's peaks in 128 columns over the loop (8 lanes, a byte each, the square root of the peak; pass 1 the first recording, each overdub cycle round the loop the next, measured on the input before the loop joins it). Free mode's first recording has no known length, so its peaks go into 256 entries that merge in pairs when full and are spread over the columns when the loop closes. The UI may be another process, so the cells travel as output parameters, each one exact integer in a float (generation, lane, column, peak; `encodeLooperCell()`): the first is the cell written last (the live picture), the other 7 go round every cell in use, moving on every 40 ms (slower than UIs read outputs), so a UI that opens later, or missed some, has the whole picture within a few seconds. Clear starts a new generation, and the UI drops cells of other generations. The UI keeps its copy (`looperOutput()`) and draws the page (`drawLooper()`). Chains with the old block: `retireLoopers()` takes Looper blocks out, moving MIDI mappings to the global controls; from a project (host state or the exchange file) the first one's settings go to the global looper and the chain is sent without it; from a preset or undo it's just dropped. The block type stays registered, and hidden from Add Block, so a chain with one still builds if no UI opens. **Memory** (owner, 2026-11-01: an instance that never uses the looper reserves nothing, and the looper is ephemeral): the 23 MB loop buffer is allocated only once the looper is wanted in this run: the UI pulses the hidden Looper Wake parameter (1 for 250 ms) when the page opens, or a footswitch control is pressed (MIDI); the audio thread latches that (`fLooperWanted`), and the plugin's exchange thread allocates (`Engine::serviceLooper()`, every 30 ms) and hands the buffers over through an atomic flag (`Looper::attach()`). Until then the looper passes audio through, and a Rec/Dub press waits for the memory. Since the pulse is over long before a save, projects hold 0 and reopen without the memory. The old block still allocates its own, as it did. **Saving the loop** (owner, 2026-11-01: WAV and FLAC; MP3 and Opus were left out, since they'd need encoder libraries and LAME's LGPL doesn't suit an MIT plugin): the page's Save WAV… and Save FLAC… buttons (while the loop plays or is stopped, when the audio thread doesn't write it) pick a file with the system dialog, then bump the hidden Looper Export counter; the plugin's exchange thread writes the loop as a 32-bit float WAV to the cache dir (`looperExportFile()`, `Engine::looperWav()`, which reads the buffers the audio thread only reads in those states) and answers in the hidden output Looper Exported (counter * 2 + 1 if written); the UI reads that file, deletes it, and writes the chosen format (`src/state/AudioFile.*`): a 24-bit PCM WAV, or a 24-bit FLAC from our own encoder (fixed predictors of order 0-4, partitioned Rice coding, the best of the four stereo modes per 4096-sample block, MD5 unset; decodes bit-exactly in ffmpeg, `tests/AudioFileTests.cpp`; about 9% larger than ffmpeg's LPC encoder on a guitar recording). The file route works where the UI is another process and its state messages don't reach the DSP (Reaper's LV2). **Passes, each in its own lane** (owner, 2026-11-01: any pass can be deleted): the loop's memory is `LooperMemory` (in `Looper.hpp`), up to 8 lanes of two channels. The audio thread takes a lane for each pass with a lock-free state per lane (none, ready (zeroed), used, given back, busy: `take()`, `give()`) and plays the lanes summed; an overdub scales every lane at the write position by Feedback and adds the input to its own pass's lane, so the sum is exactly the old single buffer. A first recording may take a given-back lane unzeroed (it writes every sample it plays); overdub passes need a zeroed one. The exchange thread's `Engine::serviceLooper()` calls `LooperMemory::service()`: it zeroes lanes given back and keeps one ready lane long enough for the next pass (the looper's `setWant()`: a minute with no loop, the loop's length with one, nothing while a free recording's length is unknown), allocating only when none fits. So the memory is 23 MB for the first recording plus the loop's length per pass after it, up to 8 lanes (8 x 23 MB at worst for a minute-long loop). With no lane to be had, a pass joins the last one (as passes beyond 8 always did). The old block services its memory only in `prepare()`, so its overdubs all go into one lane, as before. Deleting a pass (`Looper::deletePass()`; not the one being recorded; the only one left clears the loop) gives its lane back, moves the later lanes up and starts a new waveform generation; the UI moves its own copy up at once and keeps it when that generation arrives. Export (`looperWav()`) sums the lanes in use (`LooperMemory::mixdown()`). The page sends deletes and the start marker through hidden counter parameters, Looper Delete (counter * 8 + lane) and Looper Start (counter * 1001 + where in 0..1000), which the engine acts on only when they change, not as a project restores them. **Count-in to an overdub** (Count In mode, Rec/Dub with a loop playing or stopped; `LooperState::DubCountIn`): the clicks follow the loop's beat (the count-in's for a Count In loop, else the loop split into the whole number of beats at BPM nearest its length) and Beats; playing, the pass starts at the loop's start, the first time that leaves room for Count-In clicks (they wait until then); stopped, the loop waits in silence through the count-in and starts with the pass from the start marker. The pass's writes begin a round trip (Latency) later, so the first lands at the loop's start; it records Loops passes with the click, then plays on. A press during it calls it off, Play/Stop stops. Half Speed's beat is in samples heard. **Start marker** (`Looper::setStart()`): Play, and an overdub from Stopped in Free mode, start there; while the loop plays (not while it overdubs or counts in) it jumps there at once (owner, 2026-11-03), crossfading over 256 samples from where it was (`fJumpFrom`, `fJumpLeft`); Clear resets it.
- **Looper** (the block, retired 2026-11-01; all of this is the global looper's behaviour too): a fixed buffer of 60 s at 48 kHz per channel (23 MB), allocated in `prepare()`. Its status (state, length, position) is encoded in the block meter (`LooperStatus`) and drawn in the panel (`MeterStyle::Looper`). The loop survives chain edits (the engine reuses the block) but not a sample-rate change. **Count In mode** (owner, 2026-10-30; the default): the first Rec/Dub starts a sample-counted timeline with the settings of that moment: Count-In clicks (`LooperState::CountIn`), then a recording of exactly Measures x Beats beats at BPM (at most the buffer), which closes the loop by itself, then Loops - 1 overdub passes; clicks sound on every beat (`round(k * beat length)`) until the last pass ends, the first beat of each bar accented (bars start where the recording does), with the metronome's Classic sound (`classicMetronomeClick()`). They're added after the loop has taken its input, so they're never recorded. A press during the count-in cancels it; one during the timed recording or passes acts as in Free mode and ends the clicks. The meter shows the click being counted in, and the recording's progress (the panel shows the bar). The seven controls came after the looper's first seven; blocks saved before them lack the `"countIn"` config key, so the DSP keeps them in Free mode and the UI sets the new controls to their defaults and adds the key (`migrateBlocks()`, `kMigrations`, as for the NAM tone controls). Since 2026-10-31 the clicks go to the engine's click bus (`Block::setClickOutput()`: one buffer per thread, like the MIDI outputs, added to the output with the metronome after the output level), so the blocks after the looper don't touch them; Click goes to 200% (its range changed before any release that had it); and Tap (a momentary control after Click; its unused value 0 is its default, so it needs no migration) sets BPM from the taps' average (`TapTempo`, `src/engine/TapTempo.hpp`, which the metronome's tap button uses too). The UI times the same presses (`watchLooperTap()`, also for MIDI-mapped ones) and sets the BPM control to match, so the knob shows the tempo. **Latency** (owner, 2026-10-31: loops didn't come round at the right moment; the last free slot, 0-200 ms, default 10, config key `"latency"` with its own `kMigrations` entry, so a type can now have several): monitoring through a DAW, what's played reaches the plugin a round trip (output + input latency) after the sound it answers, and no plugin API reports that figure. Count In mode records from the downbeat's click plus the round trip, for exactly the loop's length, so buffer index k is grid position k. The loop comes round on the grid's next downbeat, playing from index 0, while the bar's last round trip (still arriving) is written into the loop's end (`fTailPos`, then the seam's crossfade), which plays only on the next time round (owner, 2026-10-31: it used to close a round trip after the downbeat and play on from that far in, which cut the first repeat's downbeat attack: a pause before the riff came back). A Latency above the real round trip clips the downbeat's attack; one below it plays the loop that much late, so too low is the safer error. The overdub passes end that much later, the clicks still on the grid (`fClickEnd`). Overdubs in both modes are written a round trip behind the playback position (times the playback step: Half Speed, Reverse), where what the player heard sits. Free mode's recording is left as it was (its start and end are presses, whose own delay is unknown). The seam (both modes): the loop's last 256 samples crossfade into the 256 samples before its first one (a ring of the latest input, `fRecent`, copied when a recording starts), instead of both ends fading to zero, so a downbeat at the start keeps its attack.
- **Spring reverb**: two springs, each a loop of 60 stretched first-order allpasses (the dispersion that makes the chirp), the transit delay and damping; after Välimäki, Parker and Abel (2010), simplified.
- **Tests**: `tests/BlockSanityTests.cpp` runs every registered block at default, extreme and random settings, at 44.1/48/96 kHz, mono and stereo (finite, bounded, no allocation, silent for silence), and for ten seconds at its maximum to check that no feedback loop grows once the input stops. `tests/PedalTests.cpp` and `tests/DriveTests.cpp` check each pedal's behaviour (gains, notches, rates, intervals, aliasing, looper actions).
- Voicing is by measurement, not by ear; the owner tunes the sound.

- **Add Block's live preview** (owner, 2026-10-31): picking a block in Add Block or Replace Block (a click, or the arrow keys: Up/Down through the rows, Left/Right too in the block types' two-column grid) puts it in the chain at once, so it can be heard; each new pick takes the previous one out. The first pick snapshots the chain (`fPreviewBase`, and where the block goes); each pick restores the snapshot (values back in the host too, since a replaced block's slot may be reused) and adds the block without an undo step. OK (Add/Replace), Enter or a double-click keeps it as one undo step from the snapshot; Cancel, Esc, × or a click outside restores the snapshot. Picks are identified across frames by file path or typeId (`pickKey()`), since the rows are rebuilt as they're drawn.

- **Phase check** (owner, 2026-10-31): `compareBranchPolarity()` (`src/engine/PhaseCheck.*`) builds private copies of each split branch's NAM and IR blocks (others are left out: they rarely flip polarity, and time-varying ones would blur it), runs 0.5 s of quiet band-limited noise (80 Hz to 5 kHz, about -30 dBFS, so amp models stay near-linear) through each branch at 48 kHz, low-passes both at ~400 Hz (the out-of-phase sum is heard as lost low end, and up there two cabs' timing differences would flip the sign), and takes the correlation with the largest magnitude within ±0.5 ms of Align's delay: ≥ 0.5 same, ≤ -0.5 opposite, else unknown (no warning). The UI runs it on its own thread (`PhaseWorker`, joined on close, cancellable) 600 ms after the inputs last changed (`phaseKey()`: those blocks' configs, values and bypass, and Align), so a knob drag starts one check at its end; a check costs a few tens of ms (two NAM model loads included). The Invert switches are applied to the result in the UI, so flipping one needs no new check.

## 5. Plugin state, presets and settings

- **Plugin state** (saved by the DAW with the project): a JSON string through DPF's state API, holding the chain, slots, split, block settings, MIDI mappings and metronome settings. File references store the path and the content hash.
- **Preset files** (`.xythos`): a zip containing `preset.json` (the chain, its MIDI map and the global sound controls) and, when exported with "embed files" on (default on), the NAM files and IRs it uses, under `files/<content hash>/`, and the user's images its blocks use, under `images/<amps|cabs|pedals>/<id>` (added to the user's libraries when it's opened: an identical image is reused, a name taken by other content gets a number and the blocks follow). Save and Save As keep presets in the preset folder (`presets/` in the config dir, with subfolders), without files, through an in-app dialog; Export writes an embedded copy anywhere through the system dialog; Open File… opens one from anywhere. Manage Presets… loads saved presets, marks one as the default, which new plugin instances load, and deletes them (Delete asks "Delete?" and deletes on a second click; only preset files inside the preset folder, `deletePreset()`). Rename (owner, 2026-11-08) edits the row's name in place (`kFieldPresetRename`; Enter or a click elsewhere commits, Esc cancels) and `renamePreset()` renames the file in its own folder, refusing a bad name or one already taken (a change of case only is allowed); the default, the preset's Program Change, the recent list and the open chain's preset path follow the new path. The top menu has New, Save, Save As, Manage Presets…, Open File…, Export…, the embed option, and every saved preset laid out as the preset folder is: top-level presets first, then each folder as an indented heading with its presets and subfolders under it (the open preset in the highlight colour, the default marked). It scrolls when it's taller than the window. The preset name shows in the top bar, with a dot when the chain has changed since it was saved or opened.
- **Missing files**: on load, each block's file is looked for at its original path, then as an embedded copy (extracted to the cache), then in the library by content hash. If none is found, the block is created grayed out (passes audio through) with "Locate…", and "Use … from the library" when a library file with the same hash appears later.
- **Settings and favorites**: one JSON file per user — `~/.config/xythos/settings.json` on Linux, `%APPDATA%\Xythos\settings.json` on Windows. It's written atomically, and every open instance reloads it when it changes (the UI checks its modification time once a second; a change re-reads the file before saving, so instances don't overwrite each other's changes). Fields: NAM folder, IR folder, default A2 size, normalization default for new blocks, multi-core splits, the theme (`theme`, a name in `ink::themes()`; Iris to start; the earlier accent and highlight keys are ignored), favorites. A `blockArt` key from older versions is ignored. Also the update check on/off and the dismissed release (`checkUpdates`, `dismissedUpdate`).
- **Update check** (`src/state/UpdateCheck.*`): while it's on (Settings, default on), the UI checks a few seconds after opening, at most once a day for all instances together (`update-check.json` in the cache dir: when the last check started and the latest version found; claimed before fetching, so instances opening together don't all check, and a failed check also waits a day). `UpdateChecker` fetches GitHub's `releases/latest` (drafts and pre-releases excluded; tags like `v1.2.0`) on its own thread through `HttpGet` (`src/ui/HttpGet.*`: WinHTTP on Windows; the `curl` command on macOS and Linux, so the plugin links no TLS library, HTTPS only), cancelled and joined when the UI closes. A newer version than this build (`XYTHOS_VERSION`, the CMake project version, which `getVersion()` also reports) shows as a notice after Redo in the top bar; clicking opens the releases page (a fixed URL, never one from the response), × stores the version as dismissed. Nothing is downloaded or installed.
- **Favorites** are stored by content hash (XXH3-128 of the file bytes).
- **Undo/redo**: a stack of `ChainState` snapshots (small, so snapshots are cheap), up to 200 steps. One knob gesture is one step. It covers blocks, block values, bypass, the MIDI map and preset loads, not the global knobs. Undo/Redo buttons in the top bar; Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y while the window has focus.

When a block uses one, the file is extracted to the cache directory (`cache/extracted/`) off the audio thread and loaded from there.
- An index cache per kind (path, size, modification time, hash, metadata) keeps rescans fast. Only new or changed files are read and hashed. A rescan runs when the UI opens, when a folder changes, and from the Rescan button.
- NAM metadata (gear make/model) is shown under each model in the list, with its gear type and architecture (`describeNamFile()`, `namGear()` in `src/state/Library.*`). ## 7. User interface

- DPF UI with NanoVG drawing. Resizable, with HiDPI scaling. The default logical size is ~1200 × 720 and the smallest layout ~900 × 560; the window can go down to 40% of that (owner, 2026-11-07: small screens), and below it `uiScale()` multiplies the host's scale factor by the fit, so the whole UI shrinks evenly (logical `fWidth`/`fHeight` never go under the smallest layout). Drawing and mouse input both go through `uiScale()`.
- Layout:
  - **Top bar**: the logo (two embedded layers, `resources/logo/`: the crop circle in white, tinted with the highlight colour, and the wordmark), preset menu and preset name, undo/redo, the update notice when a newer release exists (section 5); on the right, icon buttons for the GitHub link (the GitHub mark in outline; opens the project's page), the Fretbored link (the Fretbored app icon, drawn flat in the icon colour from its `assets/icon.svg`: faint strings and frets, the notes spelling an F as rings, the root's heavier, after Fretbored's Ring look, 2026-10-30), the metronome (with ▾ for its panel), the tuner, settings and global bypass.
  - **Middle**: the chain, left to right, with square block tiles and "+" boxes. A split shows as two rows that rejoin at the merge. Hovering the gap between two blocks shows two small buttons: insert a block there (upper half) and, with no split yet, split there (lower half). A chain wider than the window scrolls with the mouse wheel, a thin scroll bar under it, or a middle-drag anywhere over it but a block. Middle-clicking a block enables or bypasses it (owner, 2026-10-30; from 2026-10-24 it removed it). Double-clicking a block, or Replace in its right-click menu, opens Add Block on the block's own category and puts the new block in its place and slot (one undo step). The block menu: Enable/Bypass, Replace, Remove, Copy, Paste after (once a block is copied), MIDI Learn bypass (and Clear MIDI when mapped). Copy takes the block's type, settings, values, bypass and image, not its MIDI mappings; the copy is shared by the instances in the host's process, so it pastes into another instance too, and right-clicking a "+" box pastes at the end of that section (owner, 2026-10-29). A paste is one undo step and takes a free slot. The mouse wheel over any knob turns it (2% a notch, Shift 0.2%; a burst of notches on one knob is one undo step).
  - **Below the chain**: the selected block's panel: a large block image on the left (placeholder art until real pedal/amp/cab images exist), the name and file above the controls, and the generic controls centred in the space right of it in one or more rows, spread out up to 1.6x their cell width and 1.35x their row height to fill it (owner, 2026-10-28); dark gray while the block is bypassed. The image is meant to fill the panel's height (owner, 2026-10-25): the controls go into as many rows as needed (and as fit) for that, and the image only shrinks when even that leaves too little width. The generic knobs may later go away in favour of turning knobs on the image itself.
  - **Bottom bar**: mono/stereo toggle, input, bass, middle, treble and output knobs, input/output meters with clip lights (click to reset), limiter on/off.
- **Interactions**:
  - Drag a block to move it; drop indicators show where it lands.
  - Right-click a block: bypass, remove, copy, paste, MIDI learn.
  - Drag a knob up or right to turn it up, down or left to turn it down (owner, 2026-10-31: left/right too, for the bottom bar's knobs); double-click to reset it (to the user's default for the block type, if set); Shift-drag for fine control.
  - Set as Default (block panel header, owner 2026-10-31): stores the block's values as what new blocks of its type start with, in `Settings::blockDefaults` (typeId -> control name -> value in the control's units, so it survives range changes; footswitch actions left out); applied in `addBlock()` after the Settings defaults (NAM/IR Normalize, A2 size); Clear Default (shown while one is set) removes it.
  - The X11 window gets an arrow cursor of its own (`defineArrowCursor()`, `src/ui/Vsync.cpp`): without one X shows the parent window's, and Reaper's FX window left its resize cursor on over the whole plugin. pugl doesn't define one (its `puglSetCursor()` skips the arrow it starts with).
- **Dialogs**: Add Block (categories on the left), Settings, and the Tuner and Metronome panels (overlays). Lists in dialogs (Add Block's blocks, library files and search results, the preset menu, Manage Presets, Save As's folders) show a scroll bar at their right edge when they're taller than their space, to drag or click for those without a scroll wheel (owner, 2026-10-25). Add Block's rows are tall enough to see the art (112 px for blocks, 76 px in lists).
- **Redraws on Linux**: X11 events are only read when the host calls the UI. LV2 hosts call it on their idle tick (Reaper: ~30-36 Hz), so dragging redraws at that rate. For VST3, a DPF patch (`patches/dpf/`) registers the X11 connection with the host run loop's event handler, so events are handled and redrawn as they arrive, whatever the host's timer rate. The UI turns vsync off for its GL window, so a buffer swap never stalls the host's GUI thread waiting for the screen. `XYTHOS_SHOW_FPS=1` in the host's environment shows a frame-rate readout.
- **Touch mode** (`Settings::touchMode`, owner 2026-11-08): touchscreens reach the UI as an emulated left mouse button, so `onMouse()` holds a left press back (`fTouchPending`) and decides in `onMotion()` (moved more than 10 px: the held-back press goes through `onLeftPress()` at where the finger landed and the drag continues, or a vertical drag over a dialog's list scrolls it), on release (a tap: press, then release) or in `uiIdle()` (`checkLongPress()`: held 550 ms, `onRightClick()`, else the help for what's there; the rest of that touch is swallowed). Momentary hits skip this (the looper's Rec must start on the press). `hitAt()` falls back to the nearest hit within 10 px, among what's drawn over the dialog the tap landed on. Empty chain space pans like a middle drag. `drawHelp()` shows only after a long press. Long-press timing depends on the host's idle rate (30-60 Hz), which is fine at 550 ms.
- **Hover help**: resting the mouse on a control for 0.6 s shows a translucent popup with its name and a plain-English explanation of what it does and how to use it. The texts are in `src/ui/ParamHelp.cpp` (block controls by typeId and control name, the others by parameter symbol); `tests/ParamHelpTests.cpp` checks that every block control and every global control has one, at least 80 characters long. The top-bar icon buttons and the metronome's beat, grouping and tap controls have popups too, and so does every block type (`blockTypeHelp()`: what it is, what it's for, how and where to use it), on its tile in the chain and on its entry in Add Block (categories and search results).
- A dark theme defined as colour tokens in one file, so it can be restyled: the window shows the owner's background image (`drawBackground()`, scaled to cover); what the window shows in its base state (bars, panels, tiles, buttons, the tuner and metronome) is black at 50% with 1 px gray outlines (`surface()`), and everything that appears over it (dialogs, menus, help popups, the toast) black at 95% (owner, 2026-10-29; a blur behind the popups was tried and dropped), the items listed in Add Block black at 97%, and buttons that are on are an accent outline over a faint accent tint. Knobs: hairline body, 21 ticks lit up to the value, a dot for the position. Font: Jost Light (Regular for small text), drawn 1.69x the layout size because Jost runs small, with DPF's DejaVu as the fallback for glyphs Jost lacks (★, ▾).
- **Outlines, buttons, fills and knobs in ink**: with a gradient on, the highlight colour is painted with one window-fixed image paint instead of a solid colour (`XythosUI::inkPaint()`; the paint is mapped back through the current transform, so the colours stay put wherever a shape is drawn). The texture (`state/Ink.*`, 128x80 RGBA, stretched over the window) is made when the theme changes: Smooth runs the colours left to right, slightly tilted; Splotchy is fixed two-octave value noise stretched to the full range, so the blobs look the same every time. The UI's `fillColor`/`strokeColor` shadow NanoVG's and route the highlight's RGB to the paint (alpha kept); dimmed (bypassed) colours stay grey. **Text is not painted**: NanoVG draws glyphs with its font atlas and the paint's colour alone, and an image paint's colour is white, so `text()`/`textBox()` draw ink text in its plain colour (seen in jalv on 2026-10-30; not yet tried in Reaper). Making text follow the gradient would need either a strip-by-strip scissor approximation (many draws, visible banding) or drawing text into an offscreen target and masking it, both larger changes. Colours are lifted toward white below relative luminance 0.12 (`ink::lighten()`). **Themes** (owner, 2026-11-08) replaced the accent colour, the mode choice, the presets and the colour picker: `ink::themes()` lists fixed looks (Iris first, then Kaia's), each a mode, 2-3 colours, an accent, text and dim text colours, two ARGB glows drawn over the background image (`drawThemeGlows()`, radial gradients at the top right and bottom left, sized as in Kaia) and a scanline flag (`drawScanlines()`, last in the frame). `applySettings()` sets `theme::accent`, `theme::text` and `theme::textDim` from it (`isInk()` matches those RGBs, so they take the paint), and `updateInkImage()` remakes the texture when the theme changes. The logo's crop circle is a separate white layer (`kLogoMark`) drawn with its paint's colour set to the highlight (`highlightAt()`: the texture's colour at the circle, or the accent).
- **Power LEDs**: every pedal shows an LED, lit with a glow while the block is on and dark while it's bypassed (or missing or not running), on its tile and in its panel (`drawLed()`). The drawn pedals have a red one beside the footswitch and the amps a pilot light; built-in images list theirs in `PedalFaces.cpp` (position, size and lit colour; on the photos, the indicator spot north of the footswitch, coloured like the glyph), and the UI draws over the image's own LED, so an image can show it lit or unlit. Add Block's thumbnails show none.
- The GitHub and Fretbored links open the browser through a small platform helper (`xdg-open` / `ShellExecute` / `open`). On a narrow window the preset button narrows (down to 160 px) so both links still fit; while a MIDI learn message shows in a window under 1200 px, they make room for it.

## 9. Performance targets

- An empty chain uses under 0.5% of one core at 48 kHz with a 64-sample buffer.
- Engine overhead around blocks stays under 5% of the blocks' own cost.
- Changing a model or editing the chain causes no dropouts or clicks.
- The UI opens in under 300 ms.
- A library rescan of 1,000 files with an existing index takes under 1 s.

## 11. Decisions log

1. **CPU baseline**: AVX2/FMA is required.
2. **Standalone app**: dropped for now; VST3 and LV2 only.
3. **Reverb types**: room, hall and plate.
4. **Test DAW**: Reaper is the primary host.
5. **Compressor**: added to M3, studio style (owner's choice over a simple pedal-style one).
6. **Theme**: no gradient; pure black window. Boxes were flat near-black gray at first; the owner then chose black boxes with hairline gray outlines, Jost Light and tick-scale knobs with a dot, from drafted screenshots (fonts, knobs and surfaces; 2026-10-22).
7. **Block panel**: large block image on the left, generic knobs centred in the space to its right (were right-justified until 2026-10-28).
8. **Folder choice**: DPF's file browser can't pick folders, so "Choose…" opens the system's folder picker (`src/ui/FolderPicker.*`, on its own thread): Linux tries the desktop portal (FileChooser v3, `directory`), then zenity, then kdialog; Windows uses IFileOpenDialog with FOS_PICKFOLDERS; macOS runs AppleScript's `choose folder` through `osascript` (its own process, so it needs nothing from the host's main thread). With none of these, it falls back to DPF's browser and takes the folder of any file picked in it. The path can also be typed or pasted.
9. **MIDI map in the chain state** rather than a separate plugin state, so it follows the chain's routes (including the exchange file for Reaper's LV2) and is covered by undo and presets.
10. **Metronome samples**: only the Classic clicks come from Fretbored. Its Digital samples carry a third-party artist credit (owner's call to remove them), so the Digital sound is generated in code.
11. **16 parameters per block** (was 8), for the Doppelganger Delay. Most host parameter indices moved, which was fine only because nothing was released yet; from v1.0 on the count is fixed.
12. **Pedals before v1**: the owner asked for a wide pedal set first (no rush to v1). Varieties are a Type choice inside one block rather than separate blocks; a released Choice list never changes (saved values would map to other choices), so new varieties that don't fit become new blocks.
13. **Pitch effects without latency**: delay-line pitch shifting with pitch-synchronous splices (polyphonic, clean on notes and most chords) instead of FFT or PSOLA methods that add latency; the synth, harmonizer and octave track pitch with YIN on a decimated copy (detection takes 4-24 ms, but adds no latency to the audio).
14. **Looper controls as momentary parameters**, so footswitches map to them with MIDI learn; the looper keeps one loop (60 s at 48 kHz).
15. **macOS** (owner, 2026-10-24; was out of scope): a universal binary (Apple Silicon and Intel), macOS 11+, VST3, LV2 and AU (Logic and GarageBand only load AU). Linux and Windows stay x86-64 only. No Developer ID yet: CI signs the bundles ad hoc (Apple Silicon won't load unsigned code), so downloads need `xattr -dr com.apple.quarantine`.

16. **Pedal photos embedded** (JPEG, WebP since 2026-10-28) (owner, 2026-10-28): every pedal has a photo with knobs, a power LED and a footswitch on its face. The images stay inside the plugin rather than in files beside it: at about 30 KB each (JPEG; 3.5 MB with thumbnails) they barely grow it, embedded data costs no RAM until read, and there's no resource folder to find or lose per format (VST3, LV2, AU bundles) or per host process. Only the JPEGs are committed; the build turns them into C++ (`cmake/EmbedBlockImages.cmake`). The UI decodes only what it shows, uses thumbnails for tiles and lists, and keeps at most four full-size images. Worth revisiting only if images grow to tens of MB (e.g. much higher resolution): then a resources folder in each bundle, read through DPF's `getResourcePath()`. 2026-10-28: doubled to 1280 px after the owner saw compression artifacts, and moved to WebP q96 (11 MB; the owner approved adding libwebp v1.6.0, decoder only; JPEG XL compresses a little better but its library is much heavier); still embedded.

17. **User images in the config directory, not sidecars** (owner, 2026-10-29): users add their own amp, cab and pedal images to libraries in the config dir (copied in, so they survive moving or deleting the original) and pick one per block, instead of an image file next to each NAM file or IR. Any block can have one, not only NAM and IR blocks. They're drawn as static images (no face knobs, LED or footswitch: those are placed for the built-in photos only), and a deleted image's blocks fall back to their stock look.

18. **Update notice, not self-update** (owner, 2026-10-29): the plugin only tells the user a new version exists and links to it. Replacing its own files from inside a DAW runs into locked binaries on Windows, admin-only install folders, several loaded instances and hosts, macOS signing and quarantine, and would make the plugin a channel for running downloaded code; an installer or update app outside the DAW is the place for that, if ever. The check is opt-out in Settings and sends nothing but the request.
19. **Renamed to Xythos** (owner, 2026-10-29; was NAMsayin; the repository too): the name, the developer shown in hosts (Xythos, was the owner's username), the bundles, the preset extension (`.xythos`), the config and cache folders and the LV2 URI (`https://github.com/singularity098/xythos`) all changed, with no migration (the owner moved their own files). The VST3 and AU IDs (brand `S098`, plugin `NMsy`) stay as they were: hosts never show them, and keeping them lets projects saved with the VST3 or AU find the renamed plugin. LV2 projects saved before the rename need the plugin re-added.

20. **Hostile files: patched NAM Core, our own image decoding** (owner, 2026-11-02, after fuzzing found both): presets, models and images are shared, so a crafted file must fail to load, never corrupt memory. NAM Core v0.6.0 (still the latest) reads a model's weights unchecked, so a `.nam` with fewer weights than its config needs read past the end of the vector, a missing config key was read with `operator[]` on a const JSON object (undefined), an LSTM with no layers read layer -1, and WaveNet layer arrays whose sizes don't chain made release-mode Eigen read out of bounds; `patches/nam/` swaps its weight iterator for a bounds-checked one that throws, reads keys with `.at()`, and refuses impossible LSTM and WaveNet sizes, applied at configure time on every platform (upstream has no fix yet: worth offering it). DPF's NanoVG decodes PNG and JPEG with a bundled stb_image from 2016 that a crafted JPEG makes write out of bounds; the UI now decodes them itself with a current stb_image (submodule `deps/stb`, v2.30, PNG and JPEG only, at most 16384 px a side and 50 megapixels, checked from the header first) and hands NanoVG RGBA, as it already did for WebP.

21. **HQ pitch shifting with Signalsmith Stretch, opt-in** (owner, 2026-11-07): an optional Quality: HQ per pitch block rather than replacing the delay-line shifter, because the spectral shifter needs about 150 ms of latency for clean chords, too much to play against live; the zero-latency default stays. Signalsmith Stretch is vendored with pitch-accuracy fixes (4.11, "HQ pitch shifting"). It doesn't find notes, so it can't replace the PolyNoteFinder (the Poly Chip and MIDI Out still need note numbers).

22. **Polyphonic tracking deactivated** (owner, 2026-11-08): the PolyNoteFinder's two users are switched off, not removed. The Poly Chip is hidden from Add Block like the retired Looper block (`addItems()`), but stays registered so saved chains still build. MIDI Out ignores Mode (`kPolyEnabled = false` in `MidiOutBlock.cpp`, so a project saved with Poly sends Mono) and its panel hides Mode and Focus; the Choice list keeps both labels, since a released list never changes. Bringing either back is a flag and a filter.

23. **The poly note finder rewritten, polyphonic tracking back on** (owner, 2026-11-09: "rewrite the poly tracking if needed from scratch", then "re-enable the poly chip pedal so that I can test"): a spectral-peak finder with the single-note tracker alongside replaces the semitone filter bank, because the filter bank's failure on the new recordings was structural (a semitone band can't tell a string's harmonic from a note, and 328 s of its 401 s of stray notes were that), not a matter of thresholds. The Poly Chip is in Add Block again and MIDI Out's Poly mode, Mode and Focus are back: decision 22's commit undone (its `kPolyEnabled` flag and UI filters are gone; `git revert` of this one's part brings them back). The finder's bands start at A0 (were B0), for a bass in drop A; band numbers aren't stored anywhere. The recordings are kept as 16-bit FLAC (dithered from the owner's 24-bit; 19 MB against 66 MB), the note lists are generated (`tools/annotate`) so they can be remade, and the benchmark's bounds are per set of clips. See 4.11, "Tracking rework on the 7-string and bass recordings", for the numbers and for what the new finder does worse.

24. **Poly as a mode of every pitch-following pedal, the Poly Chip removed** (owner, 2026-11-10): a Tracking button (Mono by default, or Poly) on each block that follows notes, stored as the block config `"poly"` rather than a host parameter (no slot migrations, and Choice lists are fixed once released), so switching rebuilds the block like Quality does. The synths' voices are more instances of the same synth (`Voiced<T>`), not a per-voice rewrite of 20 synths: costlier in memory in Poly (six copies), nothing in Mono. The Poly Chip's typeId `polychip` is no longer registered; chains with one are converted to a Chip Synth in Poly wherever a chain comes in (`retirePolyChips()`), since a chain with an unknown type fails validation as a whole. See 4.11, "Poly tracking on every pitch-following pedal".
